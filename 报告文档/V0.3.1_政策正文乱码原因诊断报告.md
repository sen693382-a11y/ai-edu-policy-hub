# V0.3.1 政策正文乱码原因诊断报告

> 本轮只排查并修复"政策正文提取异常"，未重构 AI 综述助手，未修改已确认的悬浮窗口交互流程，未发送任何真实模型 API 请求。

## 一、结论速览

| 问题 | 答案 |
|------|------|
| 本次问题的真实原因 | PDF 使用**方正书版（FzBookMaker）自定义子集 CFF Type1 字体**，字形到 Unicode **缺少 ToUnicode 映射**，任何文本提取器都无法还原汉字 |
| PDF 本身是否损坏 | **否**。PDF 视觉渲染完全正常（9 页中文正文可读），是字体编码层不可提取，非文件损坏 |
| 原提取逻辑不足 | 只判断 `body_len ≥ 100` 就标记"可读"，**没有任何正文质量检测**（不查乱码、不查中文占比） |
| 为什么错误内容被判"可引用" | `extract_pdf` 对所有段落一律 `quotable=True`，且乱码文本无中文句末标点 → 全部拼成 1 段 → `body_len=18695` 轻松通过 `≥100` 门槛 |
| 采用的修复方式 | **方案1（官方 HTML 替代）** + **新增轻量质量检测**（双管齐下） |
| 实际恢复了多少文件 | **1 份**（北京方案，乱码 PDF → 官方 HTML 正文，40 段/35 段可引用） |
| 还有哪些文件无法可靠提取 | 6 份：3 份老式 `.doc`（已知不支持）+ 1 份扫描件 PDF + 2 份常州 HTML 正文过短（另 1 份空正文） |
| 可读文件数量变化 | 65 → **61**（修正 4 份误标 + 恢复 1 份） |

## 二、任务一：错误定位（真实原因）

### 2.1 诊断路径

沿 `原始PDF → pypdf提取 → 正文清理 → 段落切分 → 可引用判定 → JSON索引 → 网页预览` 逐环节检查，定位结果如下：

| 环节 | 状态 | 说明 |
|------|------|------|
| 原始 PDF | ✅ 正常 | 9 页，视觉渲染正常，中文可读 |
| pypdf 提取 | ❌ **乱码起点** | 输出 18300 字符，中文仅 0.9%（165字），`/Gxx` 字形标识 4373 处 |
| 正文清理 | ❌ 未拦截 | `extract_pdf` 没有乱码检测 |
| 段落切分 | ❌ 异常 | 乱码无中文句末标点 → 18695 字被合并为 1 段 |
| 可引用判定 | ❌ 误判 | 所有段落一律 `quotable=True` |
| JSON 索引 | ❌ 继承错误 | `BJ-8B98CF` 记为 1 段可引用 |
| 网页预览 | ✅ 忠实显示 | 网页只是如实展示了错误索引，**自身渲染无 bug** |

### 2.2 乱码最早出现位置

**pypdf 提取这一步。** 原始 PDF 本身正常，乱码在文本提取时产生。

### 2.3 是否因内嵌字体缺有效字符映射导致

**是。** 诊断日志明确显示 PDF 使用 `FzBookMaker`（方正书版 maker）生成的自定义子集 CFF Type1 字体，例如：

```
/BaseFont /ZEMBGG+FzBookMaker0DlFont00536871214  /Subtype /Type1
/Encoding (自定义, 无 /ToUnicode)
```

这类字体是"字形子集 + 自定义编码"，**不包含 Unicode 映射表（ToUnicode CMap）**。提取器拿到的只是字形编号，pypdf 把编号渲染成 `/G21/G22/...` 形式。

### 2.4 为什么其他提取器也不能正确输出中文

对比测试结果：

| 提取器 | 中文占比 | 表现 |
|--------|----------|------|
| pypdf | 0.9% | 输出 `/G21/G22/...` 字形编号 |
| PyMuPDF | 3.4% | 输出 `!"#$%&'()...` 占位符号，`/Gxx` 为 0 |

两者都**无法还原中文**。原因相同：字体没有 ToUnicode 映射，这是 PDF 的固有缺陷，不是某个提取器的 bug。任何基于"字体编码→Unicode"原理的工具都无能为力。

### 2.5 为什么 18695 字合并为一段

`extract_pdf` 的段落切分逻辑是"按句末标点（`。；;！!？?：:`）续接合并"。乱码文本 `北京市人民政府公报/G21/G22...` 中**几乎没有中文句末标点**，导致整份文件从头拼到尾，只有 1 段。

### 2.6 为什么明显异常内容仍判"可引用"

`extract_pdf` 返回的 `paragraph_meta` 对所有段落硬编码 `{"locatable": True, "quotable": True}`，而 `main()` 里 `ok = body_len >= 100` 是唯一门槛。18695 字远超 100 字，于是被判"可读"且"1 段可引用"。

### 2.7 网页是否只是忠实显示错误索引

**是。** 网页预览逻辑 `ai_win.js` 只是读取索引里的 `paras` 并渲染，无渲染错误。问题 100% 在索引生成阶段。

## 四、任务三：质量检测机制（核心修复）

在 `build_index_v03.py` 新增 `pdf_quality()` 函数，多指标检测：

| 检测项 | 规则 | 结果 |
|--------|------|------|
| `/Gxx` 字形编码 | `≥ 50 处` | 判异常 |
| 有效中文占比 | `≥200字 且 中文 < 15%` | 判异常 |
| 有效中文占比偏低 | `≥200字 且 中文 < 30%` | 判异常（建议抽查） |
| 空正文 | 提取为空 | 判异常（疑似扫描件） |

同时修正两个判定逻辑：

1. **`readable` 判定收紧**：`quotable_count == 0`（无可引用段落）时，即使 `body_len` 达标，也**不标"正文可读"**。
2. **官方 HTML 替代机制**：新增 `OFFICIAL_HTML_OVERRIDE`，本地 PDF 乱码时优先用官方 HTML 提取正文，并标记 `container = "official-html"`。

**关键原则**：异常文本不标可读、不标可引用、不进正式生成；但**不修改 A/B/C 分级、不修改官方来源核验结果**（二者与"正文能否提取"是独立维度）。
